# Архитектура агента

Документ описывает текущую реализацию в `agent.py` и `agent_core/`.

## Цикл агента

```mermaid
flowchart TD
    A[Agent.act(env)] --> B[Подключить priors_history.get_prior]
    B --> C[build_cells(env.customer_profile)]
    C --> D[Создать Posterior и LLMAdvisor]
    D --> E[Explorer.candidates: крупные ячейки и цели по prior mean]
    E --> F[Round 1: до 10 пилотов по 150 клиентов]
    F --> G[env.run_pilot: SMS, фильтры tariff + arpu_segment]
    G --> H[Posterior.update: байесовское обновление]
    H --> I{Есть открытые лидеры для подтверждения?}
    I -->|нет| J[Завершить исследование]
    I -->|да| K{LLM включён?}
    K -->|да| L[Опционально: переставить top-6 лидеров]
    K -->|нет| M[Детерминированный порядок Explorer]
    L --> N[Round 2: пилоты по 200 клиентов]
    M --> N
    N --> G
    J --> O[Planner.qualifying: gate достаточности + LCB]
    O --> P[Выбор канала и разбиения под бюджет, охват, лимиты кампаний]
    P --> Q[Кампании; если ни одна не прошла — одна fallback push-кампания]
    Q --> R{LLM включён?}
    R -->|да| S[Опционально: review_finals может убрать часть кампаний]
    R -->|нет| T[Вернуть кампании планировщика]
    S --> U[Agent.act возвращает итоговый список]
    T --> U
```

`priors_history.get_prior` читает `data/change_tariff.csv` относительно расположения модуля через `DATA_PATH`. Таблица загружается лениво при первом запросе; если файл нечитаем, используется пустая таблица, а для отсутствующих пар — prior `(0.0, 0.1)`. В `Agent.act` источник prior подключается до создания `Posterior`.

Пилоты в текущем `Explorer` всегда используют `sms`. Первый раунд рассматривает максимум 10 пар ячейка–цель, по 150 клиентов на пару. Для подтверждения кандидат должен иметь положительное posterior mean и не достичь лимита в два пилота. Из таких лидеров исключаются уже прошедшие критерий планировщика. Второй раунд повторяет пилот по 200 клиентов, пока есть открытые лидеры и ресурсы среды.

Пара считается подтверждённой для итогового отбора, если выполнены оба условия:

1. `Posterior.confirmed_enough`: не менее двух пилотов **или** суммарно не менее 300 наблюдавшихся клиентов;
2. posterior lower bound `mean − 1.5 × sd` строго больше нуля (`FINAL_K = 1.5`).

Это gate планировщика. Если кандидат после двух попыток остаётся ниже порога, третий пилот для него не проводится (`MAX_PILOTS_PER_ARM = 2`). Ошибки `RuntimeError` и `ValueError` из `env.run_pilot` превращаются в неуспешную попытку без добавления записи в журнал.

## Модули `agent_core`

### `__init__.py`

**Роль и интерфейс.** Пакетный маркер с docstring «priors -> Bayesian posterior -> pilots -> allocation»; функций и классов не экспортирует.

**Дизайн.** В MECHANICS.md отдельное обоснование пакетного маркера отсутствует.

### `cells.py`

**Роль.** Строит агрегаты аудитории по ячейкам `(current_tariff, arpu_segment)`.

**Интерфейс.** `build_cells(profile)` принимает DataFrame профиля с `current_tariff`, `arpu_segment`, `ID_NUMBER` и `predicted_arpu`. Возвращает словарь `{(tariff, segment): {"size": int, "arpu": float}}`, где `size` — число строк, `arpu` — среднее `predicted_arpu`.

**Дизайн.** Такое разбиение соответствует единице эффекта в механике: эффект тарифа задаётся для тарифа и ARPU-сегмента; фильтры `data_segment`/`call_segment` меняют состав и размер группы, но не само отношение эффекта (MECHANICS.md, §1 и §9, пункт 1). Само описание агрегатора находится в коде, а не отдельно в MECHANICS.md.

### `priors.py`

**Роль.** Предоставляет подключаемый источник априорного распределения эффекта.

**Интерфейс.** `weak_prior(cell, target)` возвращает `(0.0, 0.1)`. `set_prior_source(fn)` устанавливает функцию `fn(cell, target) -> (mean, sd)`; `None` возвращает источник к `weak_prior`. `get_prior(cell, target)` делегирует текущему источнику.

**Дизайн.** Отделение prior от обновления позволяет `Posterior` использовать слабый prior по умолчанию, а `Agent.act` подключает исторический источник. MECHANICS.md описывает необходимость осторожных широких prior при отличии судейских эффектов от истории и доступность файла данных (§5, §6, §9, пункт 2), но не документирует этот интерфейс-механизм.

### `priors_history.py`

**Роль.** Вычисляет prior базового эффекта из исторических переходов.

**Интерфейс.** `arpu_segment(arpu)` отображает ARPU в LOW/MID/HIGH; `load_table(path=DATA_PATH)` читает CSV и возвращает статистику по `(from tariff, segment, to tariff)` либо `{}` при ошибке чтения; `prior_from_stats(stats)` преобразует статистику в `(mean, sd)`; `make_prior_source(table)` создаёт функцию источника; `get_prior(cell, target)` лениво и однократно загружает стандартную таблицу и возвращает prior. По умолчанию путь — `data/change_tariff.csv` относительно `agent_core/`.

Используются строки с `AVG_ARPU_PREV_3M >= 50`, относительное изменение ARPU обрезается диапазоном `[-1, 5]`; конверсия — сглаженная доля исторических переходов к цели. Среднее `conv × mean` сжимается множителем `n/(n+30)`, стандартное отклонение учитывает разброс и размер эффекта с нижней границей `0.05`. Для неизвестной пары возвращается `(0.0, 0.1)`.

**Дизайн.** История служит только prior, а не ответом о текущей аудитории: MECHANICS.md отмечает отсутствие пересечения ID истории и аудитории и различие исторических/судейских эффектов (§1, §5). Сжатие среднего и широкая неопределённость согласуются с рекомендацией использовать байесовское сжатие и учитывать отличие judge effects (§9, пункт 2). Подробности формул см. также в [PRIORS.md](PRIORS.md).

### `bayes.py`

**Роль.** Хранит и обновляет нормальное posterior базового эффекта для каждой пары ячейка–цель.

**Интерфейс.** `Posterior.get(cell, target)` возвращает `(mean, sd)`, инициализируя состояние через `priors.get_prior`. `update(cell, target, observed_ratio, n, mult)` переводит наблюдаемое отношение в шкалу базового эффекта, обновляет normal-normal posterior и возвращает новое `(mean, sd)`. `lcb(..., k=1.0)` и `ucb(..., k=1.0)` вычисляют границы; `confirmed_enough(..., min_pilots=2, min_n=300)` проверяет логическое ИЛИ по числу пилотов и объёму наблюдений. `n_obs` и `n_total` хранят соответствующие счётчики.

**Дизайн.** Обновление использует шум пилота `0.804 / sqrt(n)` и переводит его в базовую шкалу делением на multiplier. Это соответствует модели наблюдения и межканальному multiplier из MECHANICS.md §1–2; использование пилотов для обновления и downside gate рекомендовано в §9, пункт 2. В текущем потоке пилоты однотипны и приходят из SMS.

### `explorer.py`

**Роль.** Выбирает пилотные пары, проводит исследовательский и подтверждающий раунды, записывает наблюдения и готовит таблицу posterior для советника.

**Интерфейс.** `Explorer(env, cells, posterior, advisor=None)` принимает среду, агрегаты ячеек, `Posterior` и необязательный советник. `candidates()` возвращает пары ячейка–цель: ячейки размера не менее 300 упорядочены по `size × arpu`, а две цели каждой ячейки — по убыванию prior mean. `pilot(cell, target, n)` вызывает `env.run_pilot` с SMS и фильтрами тарифа/ARPU-сегмента, обновляет posterior и возвращает результат среды либо `None` при `RuntimeError`/`ValueError`. `posterior_table()` возвращает записи по испытанным парам с prior/posterior и свидетельствами пилотов. `run()` проводит раунды и возвращает собственный журнал пилотов с фильтрами и оценками.

**Дизайн.** Пилот по одной ячейке делает наблюдение интерпретируемым; шум, ограничения пилота и то, что фильтры нужно сохранять отдельно, описаны в MECHANICS.md §2. Выбор ячеек и целей — реализация решения «думать ячейками» из §9, пункт 1. SMS как канал пилотов и лимиты конкретных раундов заданы кодом; MECHANICS.md рекомендует дешёвое исследование и адаптивное подтверждение (§9, пункт 3), но не задаёт эти точные константы.

### `planner.py`

**Роль.** Выбирает прошедшие подтверждение пары, распределяет каналы и формирует финальные кампании с учётом ресурсов.

**Интерфейс.** `Planner(env, cells, posterior, pilot_log)` принимает среду, агрегаты, posterior и журнал пилотов. `qualifying()` возвращает для каждой ячейки одну цель с максимальным posterior mean среди испытанных, если она прошла `confirmed_enough` и `mean − 1.5 × sd > 0`. `plan()` возвращает список кампаний в формате словарей с именем, фильтрами, целью и каналом. При отсутствии пригодных кампаний создаётся одна fallback push-кампания. `SPLIT_COLUMNS` задаёт возможные разбиения по `data_segment` и `call_segment`; внутренние `_channel_options`, `_contacts`, `_best_assignment` оценивают выбор канала, охвата и денежного лимита.

Планировщик берёт цены и `conversion_multiplier` из `env.channels`, остаток охвата и бюджета вычисляет как общие лимиты среды минус затраты пилотов. Учитывает максимум 5000 контактов на кампанию и максимум 10 кампаний. Среди допустимых назначений выбирается вариант с наибольшим ожидаемым net; отрицательные варианты отбрасываются.

**Дизайн.** Ограничения охвата, бюджета, размера кампании, порядка и стоимости контактов существенны для итогового результата (MECHANICS.md §3–4); необходимость собственного учёта ресурса и распределения как knapsack сформулирована в §9, пункт 4. Требование использовать реальные параметры каналов из среды соответствует §6. Сам точный перебор разбиений и каналов реализован в коде и в MECHANICS.md не специфицирован.

### `llm_advisor.py`

**Роль.** Реальный опциональный LLM-советник, который получает posterior и может ограниченно повлиять на порядок подтверждения и состав финального списка.

**Интерфейс.** `LLMAdvisor(transport=None)` включает советника при непустом `OPENAI_API_KEY` либо при явно переданном transport. `rank_confirmations(arms, table)` возвращает порядок пар; модель может переупорядочить только первые шесть переданных кандидатов, недостающие кандидаты сохраняются. `review_finals(campaigns, table)` возвращает исходный или сокращённый список кампаний. `arm_id` формирует строковый ID пары. По умолчанию `_http_transport` отправляет запрос на chat completions; модель и base URL могут переопределяться `OPENAI_MODEL` и `OPENAI_BASE_URL`.

**Гардрейлы.** Вызовы используют `temperature=0`, JSON Schema, таймаут 20 секунд и максимум три вызова на запуск. Ответ ранжирования фильтруется по ID исходной шестёрки, дубликаты удаляются, а исключённые моделью ID добавляются обратно; модель не может добавить новую пару. При финальной проверке допустимы только имена существующих кампаний; удалить все кампании нельзя. Исключение транспорта, timeout, HTTP-ошибка, неверный JSON или неподходящий ответ дают детерминированное исходное решение. Советник записывает решения и ошибки в `log`/логгер. В основном потоке без `OPENAI_API_KEY` советник выключен. При включённом API фактический результат переупорядочивания/удаления зависит от ответа модели.

В `Agent.act` советник вызывается опционально: в `Explorer.run` — для перестановки открытых лидеров перед раундом подтверждения; после `Planner.plan` — для проверки финальных кампаний. Он не формирует и не изменяет кампании. MECHANICS.md упоминает опциональность LLM, необходимость работы без неё и детерминированный fallback (§7, §9, пункт 5), но описанные выше конкретные ограничения, JSON-схемы и порядок вызовов там не приведены.

## Точка входа

`Agent.act(env)` в `agent.py` связывает модули: подключает `priors_history.get_prior`, строит ячейки, создаёт `Posterior` и `LLMAdvisor`, запускает `Explorer`, передаёт журнал в `Planner`, затем при включённом советнике передаёт ему финальный список на review. Возвращаемое значение — список кампаний планировщика после возможного удаления отдельных кампаний советником.
